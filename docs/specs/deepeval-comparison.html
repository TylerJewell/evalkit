Akka evalkit · competitive analysis

evalkit compared with DeepEval

510 of the 514 claim-flow scenarios name a specification node, and evalkit settles every one of them without calling a model.

This analysis places an eval tree in an Akka Maven project, describes how DeepEval is built, assesses which parts can be ported under its Apache 2.0 licence, and specifies how to measure the two harnesses against each other. Figures come from the evalkit repository and from DeepEval's published documentation.

The eval tree is a separate Maven source root

Evals cost provider spend and run for minutes to hours, so they must not execute on mvn test. A source root at src/eval/java, added only under a Maven profile, does not compile on a normal build. Placing the same code under src/test/java puts an exclusion pattern between a pull request and a provider bill.

The proposed folders map onto types that already exist. dataset/ holds ScenarioSource, Scenario and Precursor. runner/ holds CampaignPlan, CampaignRunner, Lanes and the SystemUnderTest adapter. scorer/ holds everything that turns a transcript into a RunOutcome. reports/ holds CampaignReport and RunSummary. The layout makes the existing seams visible and moves no responsibility.

Surefire runs **/*Test.java under the test source root by default. Code placed there is compiled by testCompile whether or not it is meant to run, so the safeguard against an accidental campaign is a Surefire exclusion or a JUnit tag. evalkit already carries a rule that a suppression list may only shrink, and a reachability audit in this repository passed for nine development stages while examining an empty search space. A separate source root removes the suppression instead of maintaining it.

<service>/ ├── pom.xml build-helper adds src/eval under the `eval` profile ├── specs/ │ └── refund-policy/ │ ├── spec.md acceptance criteria, the source of truth for spec nodes │ ├── plan.md │ └── tasks.md ├── src/ │ ├── main/java/… the service │ ├── test/java/… unit and integration tests, run on every commit │ └── eval/ │ ├── java/com/acme/evalkit/ │ │ ├── dataset/ ScenarioSource implementations, dataset loaders │ │ ├── runner/ SystemUnderTest adapter, fixtures, lane configuration │ │ ├── scorer/ │ │ │ ├── deterministic/ node match, exact match, schema, tool-call assertions │ │ │ ├── heuristic/ similarity, JSON validity, latency and token budgets │ │ │ └── agentic/ judge agents, panels, calibration │ │ └── reports/ renderers and baseline comparison │ └── resources/ │ ├── datasets/*.jsonl │ ├── rubrics/*.txt versioned, never edited in place │ └── baselines/*.json prior runs, for band movement └── target/evalkit/ rendered reports and transcripts, gitignored

A rendered report is build output

reports/ holds renderers. A rendered report belongs in target/. A prior run kept so a new run can be compared against it is an input, and it belongs in resources/baselines/ under version control.

The profile keeps evals off the normal build

<profile>
  <id>eval</id>
  <build><plugins>
    <plugin>

      <executions><execution>
        <phase>generate-test-sources</phase>
        <goals><goal>add-test-source</goal></goals>
        <configuration><sources><source>src/eval/java</source></sources></configuration>
      </execution></executions>
    </plugin>
  </plugins></build>
</profile>

Campaigns run with mvn -Peval verify. The root is added as a test source so the Akka TestKit and JUnit remain on the classpath without a second dependency block.

Akka Specify supplies the specification a scenario points at

Scenario.specNode() holds a pointer into a specification, and in an Akka Specify project spec.md is that specification.

Datasets derive from acceptance criteria instead of being written beside them, so a scenario cannot drift from the requirement it claims to exercise. Coverage becomes a computed figure, because a spec node with no scenario appears as a report line. SystemUnderTest.emittableNodes() can be checked against the spec at plan time, which is the check that would have refused the forty payment scenarios aimed at a conversation emitting a different node set.

The coverage figure needs the guard every audit in this repository needs. A check that can pass by finding nothing requires a case it is known to catch.

An /akka:eval step scaffolds src/eval/ from an approved spec, in the same position /akka:tasks occupies for work items.

The eval tree does not use the service package convention

An eval source root declares no endpoints and registers no components, so the domain/application/api convention would produce four near-empty domain packages. The evalkit library keeps that convention. The consuming project's eval tree is organised by function.

DeepEval scores a finished input and output pair

DeepEval is an open-source Python framework maintained by Confident AI, reporting more than 400,000 monthly downloads and more than 50 metrics. A test case carries an input, an actual output and optional expected output and retrieval context. A metric implements measure(), which sets a score between 0 and 1, a reason, and a pass flag against a threshold that defaults to 0.5.

test_case = LLMTestCase(
    input="What if these shoes don't fit?",
    actual_output="You have 30 days to get a full refund at no extra cost.",
    expected_output="We offer a 30-day full refund at no extra costs.",
    retrieval_context=["All customers are eligible for a 30 day full refund…"])

correctness = GEval(name="Correctness", criteria="…", threshold=0.5,
                    evaluation_params=[SingleTurnParams.ACTUAL_OUTPUT,
                                       SingleTurnParams.EXPECTED_OUTPUT])

assert_test(test_case, [correctness])        # inside pytest
evaluate([test_case], [correctness])         # standalone
for golden in dataset.evals_iterator(metrics=[correctness]): …

The pytest entry point places evals in the test suite, runs them with the test runner, and fails a build on a failing metric. That entry point accounts for much of DeepEval's adoption and nothing about it requires Python. Section 5 reproduces the entry point in JUnit and changes when execution happens.

G-Eval generates its own evaluation steps and weights the score by token probability

Given a criteria string with no evaluation_steps supplied, G-Eval first generates the steps by chain-of-thought prompting. G-Eval then scores between 1 and 5, takes the probabilities of the output tokens, and uses their weighted summation as the score, divided to a 0 to 1 scale. The weighting requires a provider that exposes token probabilities, and DeepEval falls back to plain scoring for custom models.

The DAG metric fixes the score and lets the model choose the branch

A DAG metric is a decision tree built from three node types. TaskNode extracts structured evidence and assigns no score. BinaryJudgementNode and NonBinaryJudgementNode classify evidence and branch on the result. Every path terminates at a verdict registered with add_verdict(), and the score attached to that verdict is fixed in code.

correctness = BinaryJudgementNode(
    criteria="Is the actual output correct for the input?",
    evaluation_params=[SingleTurnParams.INPUT, SingleTurnParams.ACTUAL_OUTPUT])
correctness.add_verdict(verdict=True,  score=10)
correctness.add_verdict(verdict=False, score=0)

metric = DAGMetric(name="Correctness",
                   dag=DeepAcyclicGraph(root_nodes=[correctness]))

The DAG metric is the closest construction in the DeepEval library to the routing evalkit performs in Scenario.needsJudge(). The DAG metric reduces the model calls a scored case costs, and section 6 recommends taking it.

The Python framework integrations are the part evalkit will not match. A team already writing agents in Python installs a DeepEval callback and starts evaluating the same afternoon.

The metric contract returns a float, so an unscoreable run has no representation

A DeepEval metric produces a score or raises. The documented handling for a judge that refuses or returns unparseable output is ErrorConfig(ignore_errors=True), and for a case missing a field, skip_on_missing_params=True. Both remove the run from the result set. evalkit names the missing result and keeps it in the report.

A content filter refused to score a GenUC-02 identification-failure transcript during calibration of this kit. Dropping that run would have raised the reported agreement between the judge and the human reviewer above the figure the run earned. RunOutcome is a sealed interface with four variants, and two of the four are not verdicts on the system under test.

OutcomeMeaningCounted
ScoredA judge read the reply and gave it a scoreYes
AssertedThe reply was compared against a stated answer, with no model involvedYes
NotReachedThe setup failed, or the service sent nothing backNo
UnscoreableThe judge timed out, refused, or returned something unreadableNo

The switches over these variants are exhaustive and carry no default, so a fifth outcome is a compile error at every site that must handle it. Python offers no equivalent enforcement. A Python author adding a fifth outcome finds the call sites by search, and a missed site returns the old shape at runtime.

A criteria string carries no version, so scores change meaning silently

Editing a criteria= string in DeepEval changes what every subsequent score means, and nothing records that the change happened. Scores taken before and after the edit are not commensurable and look identical in a report.

evalkit loads Rubric(id, version, prompt) from resources/rubrics/, stamps the id and version onto every Verdict, and throws from Scoring.compare when two verdict sets carry different rubric versions. Comparing across versions attributes a change in the rubric to the service being measured.

A continuous score invites an average the dataset does not support

Identical runs of this dataset scored 7, 8, 9 and 10 on the same as-specified scenarios. Measured agreement between the judge and an independent reviewer is 89 to 91 percent on clear-cut replies and 53 percent on borderline ones. A mean over scores that unstable describes the judge.

Scoring works in bands and reports movement between them. The middle band counts as undecided, because at 53 percent agreement a pass would be an invented result.

A DeepEval run spends before it discovers an unsatisfiable case

DeepEval discovers a broken case when that case executes. CampaignPlan.check validates that the target can build every named fixture and emit every asserted node before the first call goes out. Forty payment scenarios once ran against a conversation that emits a different node set, failed on every fixture and every run, and read as forty product defects. CampaignPlan.check refuses the same campaign in under a second.

A DeepEval user can build the deterministic comparison, the versioning, the banding and the plan check

A BaseMetric subclass compares deterministically. Prompt files can be versioned by hand. Scores can be banded downstream. A plan check can be written by hand. The customer writes and maintains each of those. DeepEval's defaults work in the opposite direction: use_cache is off, ignore_errors is the documented remedy for an unreliable judge, and the metric contract returns a float.

Durable execution and agent orchestration change what a campaign can guarantee

A single Python process cannot supply the properties evalkit already draws from the Akka runtime. A campaign survives a restart. A fixture writes the state that a replay spends a conversation to produce. The report states the concurrency the run sustained alongside the concurrency it requested.

A restart costs one wave

CampaignWorkflow runs in waves against a cursor and folds counts into workflow state at each transition. A restart loses at most one wave, and the wave size is a parameter. DeepEval's recovery mechanism is a JSON cache whose use_cache flag defaults to off. A six-hour run terminated at minute 200 is a six-hour run repeated.

A fixture seeds the state that a replay spends 22 messages to produce

Of 2,365 recorded scenarios, 502 carry setup, and the claim datasets run to a median of 22 messages against a single graded exchange. An evaluation harness outside the service walks those turns through the front door. evalkit, co-located with the service, writes the state into the entity that owns it. Precursor.Replay remains in the kit because a walked path is the only evidence that the state is reachable, and CampaignReport counts walked runs separately so a seeded campaign cannot claim reachability it never tested.

The report separates configured lanes from sustained lanes

Lanes.Utilisation reports mean concurrent calls in flight against the configured lane count, and states which of the two was the constraint. DeepEval exposes max_concurrent and throttle_value and reports neither figure. A campaign that requested 64 lanes and sustained 9 under provider throttling produces the same DeepEval output as one that sustained 64, and the two require opposite remedies.

A judge panel converts the 53 percent agreement figure into a per-transcript measurement

The borderline agreement figure is currently a sentence in the report. Multi-agent orchestration makes it a measurement on each transcript. Running several judges over one transcript, on different models or under different rubric lenses, produces a distribution of scores for that transcript.

Judges that agree produce Scored, and the report states that the panel was unanimous. Judges that disagree produce the undecided band, which already carries that meaning. A panel that cannot reach its quorum, because judges timed out or refused, produces Unscoreable on the same terms as a single judge. An undecided verdict then reports a measured disagreement about one transcript, in place of a band boundary someone chose.

Calibration becomes a gate on the campaign

JudgeCalibrationTest exists as a test today. As a durable component it re-measures the judge against a held-out human-labelled set, stores the agreement figure, and refuses a campaign whose judge has drifted below a stated threshold. DeepEval holds no state between runs, so it cannot compare a judge's agreement today against its agreement last month. The figure answers the question a reader of any eval report should ask about the judge and cannot answer from the report itself.

Live interactions can be scored on the same types as a dataset

DeepEval runs before deployment and provides no production feedback loop or drift detection. Akka logs every agent interaction. A Consumer samples real interactions into Transcript records, a Workflow judges them off the request path, a View projects band distribution over time, and a Timer schedules the campaign. Transcript already carries no field that distinguishes a recorded dataset from live traffic.

A decision graph expressed as a Workflow retries one branch point

The DeepEval DAG metric evaluates inside a single metric call. The same graph expressed as an Akka Workflow gets per-node retry, per-node tracing and independent step timeouts, so a branch point that stalls does not discard the branches already resolved. Four node types also map onto a sealed interface with an exhaustive switch.

Each scorer family is defined by what settles the result

FamilySettles the result byCostReport treatment
deterministic Comparison settles it. Node reached, exact match, schema valid, tool called with these arguments. Scenario.needsJudge() routes to it automatically. 0 model calls A pass or a fail. The undecided cell carries a dash, because a figure there would be a defect in the kit.
heuristic Computation over the text settles it. Similarity, JSON validity, latency and token budgets. Repeatable in execution and approximate in meaning. 0 model calls Undecided. RunOutcome holds no variant for this family and one has to be added.
agentic A judge agent or a panel reading the transcript against a versioned rubric. n model calls A band, quoted as a range, printed beside the measured agreement for that rubric.

The heuristic family needs an outcome variant before it has an implementation

A heuristic result is not Asserted, because that variant's contract is that comparison has no confidence to be borderline about. A heuristic result is not Scored, because that variant carries a rubric id and version. Adding a fifth variant produces a compile error at every exhaustive switch, which is the design working as intended. The report currently prints deterministic and judged in separate columns, so a heuristic family needs its own column or an argued reason to fold into an existing one.

A JUnit extension reproduces the authoring experience and defers execution

DeepEval fires a metric call when its test case executes. Suite cost grows linearly with case count. Continuous integration needs 10 to 15 minute timeouts, and no case can be refused before the suite starts. A JUnit extension that collects scenarios during discovery and runs one planned campaign keeps the authoring experience, spends once per campaign, and refuses an unsatisfiable class before the first call.

@EvalCampaign(rubric = "scenario-judge", version = 2, lanes = 8)
class RefundPolicyEval {

    @Eval("an authenticated customer is told the 30-day window")
    Scenario refundWindowStated() {
        return scenario("refund-30d")
            .from(fixture("authenticated-claim-open"))
            .say("What if these shoes don't fit?")
            .expect("a 30-day full refund at no extra cost");
    }

    @Eval("a delivered bag is not assessed as lost")
    Scenario deliveredBagRoutes() {
        return scenario("GenUC-16a.3")
            .from(replay("I lost my bag", "it arrived yesterday"))
            .say("so what happens now?")
            .reaches("GenUC-16a.3");   // names a node, so comparison settles it
    }
}

Each method returns a scenario instead of asserting on one. The extension collects the class during discovery, builds one CampaignPlan, runs check() and refuses the whole class in under a second when a fixture is unimplemented or a node unemittable, then executes across lanes and reports per method. A developer writes something that reads as a test and the runtime receives a plan.

A scorer returns an outcome

public interface Scorer {
    RunOutcome score(Transcript transcript, Rubric rubric);
}

A double return type can express a low score and cannot express the absence of a score. The number it returns instead lands in someone's pass rate. Returning RunOutcome keeps Unscoreable reachable from a metric.

Apache 2.0 permits porting the metric definitions

DeepEval is licensed under Apache 2.0, which permits porting, adapting and redistributing the work with the licence and attribution notices preserved. Verify LICENSE.md at the commit the port is taken from. Record the derived metric definitions and their source revision in a NOTICE file, which is also the record that supports re-syncing when a prompt improves upstream.

ComponentDeepEval implementationDisposition in evalkit
DAG node model Four node types with verdict edges, evaluated inside one metric call. Take. Maps onto a sealed interface, and reduces judge calls at branch points.
Metric definitions Prompts and assembly logic for faithfulness, contextual precision and recall, answer relevancy, tool and argument correctness. Take these. The definitions work in any language and are the bulk of what the library provides.
Agentic metric layer Six trace-level metrics covering plan quality, plan adherence, tool correctness, argument correctness, task completion and step efficiency. No test in the repository asserts a score for any of them. Take the definitions and record that no fixture reproduces an upstream value. Task completion, step efficiency, plan quality and plan adherence each carry one model-produced score. Those four metrics return an outcome from the score, and they aggregate no judgements.
Dataset format A golden and dataset JSONL shape used across the Python ecosystem. Take as an importer. An existing dataset transfers without a rewrite.

pytest entry point One metric call per test case at the moment the case executes. Adapt to a JUnit extension with deferred execution, per section 5.

Hosted platform Confident AI dataset and trace management, integrated through the SDK. Skip this. Confident AI sells it as a hosted service.

The token-probability normalisation is dropped after two measurements. The weighting requires a provider that exposes output token probabilities, and DeepEval falls back to plain scoring without them. A continuous 0 to 1 score also supports the mean that Scoring refuses to compute.

A ported metric without a calibration case is an audit that examines nothing

Fifty metrics is a large surface. A reachability check in this repository anchored its pattern on indentation that had already been stripped, matched nothing, iterated an empty set and passed for nine development stages. A faithfulness metric ported without a transcript it is known to catch behaves the same way at higher cost. Port in tiers and require a failing case for each metric before it enters the kit.

Model calls, spend and recovery cost are the measurable differences

Almost all of an eval run's wall clock is spent waiting on a model provider, so a JVM against CPython comparison would report a property of the evaluation harness and say nothing about the service under test. evalkit refuses to print that class of figure. The differences that can be measured and defended are model calls issued, provider spend, work lost to a restart, and time taken to refuse an unsatisfiable campaign.

One language comparison is worth a controlled test and no headline. Against a self-hosted or high-limit endpoint, where the provider is not the constraint, CPython's event loop and JSON handling become measurable while JVM virtual threads stay off the request path. That test states its endpoint and its concurrency and claims nothing beyond them.

The judge-call figure comes from routing. 510 of the 514 scenarios name a specification node, and Scenario.needsJudge() sends those to comparison. A DeepEval metric issues at least one model call per test case, and a multi-step metric such as faithfulness issues two to four, because it extracts claims and then verifies each one.

The setup figure comes from seeding. 502 of the recorded scenarios carry setup at a median of 22 messages, and a fixture writes that state directly.

Both figures need a stated limit. A custom deterministic BaseMetric subclass closes most of the judge-call gap, and an HTTP fixture endpoint closes the setup gap. The customer writes and maintains both, unprompted by the framework, and the resulting code is SystemUnderTest.prepare() and Scenario.needsJudge() under different names.

Benchmark protocol

  1. Fix the dataset, the target and the provider

    Run both harnesses over the same scenarios against the same service on the same model. Publish the provider and the account rate limit. A throughput figure without them cannot be interpreted.

  2. Report model calls and spend as the primary measures

    Count calls issued, input and output tokens, and provider cost. Every one of those figures is attributable to the provider's own records. Report calls whose usage the target could not see as a separate figure, and label the total a floor.

  3. Report wall clock beside utilisation

    Lanes.Utilisation already separates a lane-bound run from a downstream-bound one. A wall-clock figure without that separation supports no decision.

  4. Measure recovery and refusal directly

    Terminate both runs at the same scenario and count the work repeated. Point both at a dataset the target cannot satisfy and record the time to the first refusal.

  5. State what the protocol does not establish

    The protocol measures cost and recovery for one dataset against one target. The protocol establishes nothing about which kit scores more accurately, which is a calibration question against human labels and a separate exercise.

The figures here are estimates until the protocol runs

DeepEval's behaviour in this analysis is read from its published documentation and README. No run against this dataset was made. The call counts in section 7 are derived from documented metric shapes and from dataset statistics in this repository. Quote them as estimates.

Nothing here establishes that either kit judges more accurately. Every difference argued above concerns cost, recovery, and which numbers a report prints. Accuracy is measured against human labels, and the figure for this dataset remains 89 to 91 percent agreement on clear-cut replies and 53 percent on borderline ones. A judge panel is proposed to improve the second figure and has not been measured.

The adoption difference is real and none of this addresses it. DeepEval has the Python framework integrations, the tutorials and the download volume. evalkit returns Scored, Asserted, NotReached or Unscoreable where DeepEval returns a float, and throws on a comparison across rubric versions where DeepEval permits one.
