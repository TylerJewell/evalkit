Akka evalkit · publishing design

evalkit as a published library

Publication is blocked on a hand-built SDK. evalkit-akka pins an Akka SDK compiled from an unmerged branch, so no continuous integration job builds it and no release can include it.

The module and package layout, the API surface, and what stands between the working tree and a release. Every claim here describes code in the working tree. An earlier revision described a proposal, and the section on work the code never adopted records the difference.

Publishing readiness

The blockers below stand between the working tree and a published artifact. The SDK pin is new, and it decides the release date.

BlockerState
The SDK pin evalkit-akka depends on 3.6.0-59-7321c44b-dev-SNAPSHOT, built by hand from the feature/governance branch of akka/akka-sdk. That branch publishes no artifacts. The pin holds until the evaluation and ledger APIs ship.
Continuous integration No job can build evalkit-akka while the pin stands. evalkit-core builds everywhere and carries the whole scoring suite.
The groupId io.akka.evalkit presumes a namespace nobody has granted.
Surefire Pinned to 2.22.2 because that is the version cached offline when the build was written. Raise it against a real repository.
Rubric calibration scenario-judge v3 returns a reason on v2's bands. Whether the two agree is unmeasured, because the measurement needs the reference dataset and that dataset is not in this repository.

The licence, the NOTICE file, the contributing guide and the security policy are in place. Every metric ported from DeepEval carries a provenance entry naming the upstream class, the file and the commit.

Module design

Two modules. evalkit-core holds scoring, outcomes, metrics, scheduling and reporting, and declares no dependencies. evalkit-akka holds the durable campaign and the judge agent.

evalkit-core      scenarios, runner, scorers, metrics, reports      no dependencies
evalkit-akka      durable campaigns, agent judges                   Akka SDK

The empty dependency list on evalkit-core is a deliberate constraint. What a run reports is a question about evidence, and evidence needs no infrastructure. A service in another language behind an HTTP port implements one interface and uses the whole scoring half.

The aggregator POM parents nothing. evalkit-core has no parent, and evalkit-akka inherits akka-javasdk-parent because the TestKit needs the build configuration that parent supplies. Making the aggregator the parent broke the TestKit's own configuration.

Package design

Each package in evalkit-core collects the types that share a job.

PackageHolds

io.akka.evalkit.metricMetric, Grade, MetricRef, AlignmentMetric, and every ported metric.

The scenario and the dataset

A scenario is a record. A dataset is a List<Scenario>, and no wrapper type stands between them.

public record Scenario(String id,
                       Optional<String> specNode,
                       Optional<MetricRef> metric,
                       Precursor precursor,
                       String gradedTurn,
                       String expectedOutcome) {}

A scenario names a specification node, or a metric, or neither. Naming both is refused at construction, because the report has one row per scenario and a second expectation would settle the same run again.

Precursor reaches the starting state. Precursor.replay walks the recorded turns through the interface a user would use, which costs a model call per turn and proves the state is reachable. Precursor.fixture asks the target to write the state directly, which costs nothing and proves nothing about reachability. The report counts the runs that walked their own path.

The runner

CampaignRunner takes a checked plan and a router, runs the scenarios across a bounded pool, and returns one report with one row per scenario.

var plan = new CampaignPlan("refund-policy", dataset, Lanes.of(8), rubric);

if (plan.check(target) instanceof CampaignPlan.Check.Refused refused) {
    refused.reasons().forEach(System.err::println);
    return;
}

var result = CampaignRunner.run(plan, target, router);
System.out.println(result.report().summary());

CampaignPlan.check asks the target which states it can build and which nodes it can emit, and refuses a campaign the target cannot satisfy. A campaign that would fail at minute forty for a reason knowable at minute zero stops in the first second.

Workers pull from a shared queue. Transcripts in the recorded datasets run from 2 messages to 82, so a fixed partition would leave one worker grinding while the rest idle. Every scenario produces a row whatever happens, and the runner refuses to build a report whose outcome count differs from its scenario count.

CampaignRunner.Completed carries the outcome and the scenario together. Parallel lists indexed by position produced two separate defects, one inside the runner and one in the type it handed back, and a record holding both leaves nothing to zip.

Scorers and outcomes

A scorer reads a Observation and returns a RunOutcome. The return type is an outcome, because a double has no value meaning that nobody assessed the run.

A Observation holds a Transcript and an Evidence. The transcript carries the four fields a rubric interpolates. The evidence carries everything else the run observed: the specification node, the latency, the tool calls, the model calls, the instruction the model was given, the failure that ended the run, and the tokens. A metric reads the evidence. A judge reads the transcript alone, so its input stays byte-identical whatever else the run recorded.

OutcomeMeaningCounted
ScoredA judge read the reply and returned a grade.Yes
AssertedThe reply reached the node the scenario named.Yes
MeasuredA metric computed a number against a threshold.Yes
NotReachedThe setup never landed, or the service answered nothing.No
InconclusiveA scorer ran and reached no grade.No
FailedA scorer threw, which is a defect in this kit.No

The interface is sealed and every switch over it carries no default, so a further variant is a compile error at every site that handles one.

A scorer signals absence by returning Inconclusive, which suits a metric with nothing to measure. A judge that discovers the absence several frames inside parsing a reply throws InconclusiveScore instead, and the runner reads the exception type to tell a decline from a defect.

Metrics

Metric splits finding collection from aggregation. Collecting findings may call a model. Turning findings into a number is a pure function, so the arithmetic runs in a unit test with no provider and no key.

MetricScoresModel calls
ToolPermissionWhether an agent called only the tools it was allowed to call.0
ToolCorrectnessWhether the expected tools were called, by name, arguments, order or return.0
ArgumentCorrectnessThe share of tool calls made with arguments that serve the request.1 per call
TurnRelevancyThe share of exchanges whose reply answered what was asked.1 per exchange
TurnFaithfulnessThe share of claims a retrieved passage supports.1 per claim
CitationFaithfulnessWhether each citation supports the claim beside it.1 per citation
DagThe branch a judge chose through a decision graph.1 per branch point

AlignmentMetric covers the metrics whose score is one model call: TaskCompletion, StepEfficiency, PlanQuality and PlanAdherence. An alignment metric implements Scorer, because a single model-produced score gives aggregate nothing to work on.

PlanQuality and PlanAdherence read the plan from the reasoning a run's model calls carried. A run whose provider returned no reasoning produces Inconclusive, where the upstream these metrics were ported from scores such a run 1 and passes it.

Reports

CampaignReport counts. RunSummary renders. Neither prints one pass-rate percentage for a campaign.

The runs behind a campaign are not the same kind of thing. Averaging a borderline model grade with an exact comparison gives the two equal weight, so the report keeps comparison, computation and finding in separate columns. The undecided cell for comparison and for computation shows a dash, and a figure in that cell reports a defect in this kit.

RunSummary is terminal-width plain text written for a compliance or risk reader who does not know the service. The summary states what will be tested before the run, what was found after, the judge's bands and its measured agreement, and what the run cannot show. A total the target could not measure is labelled a floor.

Akka components

Two components. ScenarioJudge is a request-based agent scoring one transcript against one rubric. CampaignWorkflow runs a dataset in durable waves.

ScenarioJudge holds no prompt of its own. The rubric is loaded from resources/rubrics/ by id and version and passed in, so the judge is the mechanism and the rubric is the data. Memory is switched off, because a judge that remembered its last twenty scores would drift toward them and two campaigns run in a different order would disagree for no reason connected to the services being judged.

CampaignWorkflow takes a page of scenarios per durable step and folds the counts into state before transitioning. Recovery costs at most one wave. State holds counts and a cursor, because carrying thousands of transcripts through every transition would cost more than running the campaign.

Work the code never adopted

An earlier revision of this document proposed an API the code never adopted. The reference documentation was written from that proposal, and every source link in it resolved to a file that does not exist. Observation the difference stops that happening again.

ProposedWhat exists
evalkit-formats, evalkit-junitNeither module was built. A campaign runs as an ordinary JUnit test with no extension, and no dataset importer ships.
scorer.deterministic, scorer.heuristic, scorer.agenticThe scorer types live in domain and the metrics in metric.
NodeMatch, ExactMatch, JsonSchemaMatch, ToolCallMatchSpecNodeMatch is the only comparison that was written.
LatencyBudget, TokenBudgetNeither exists. Evidence records latency and tokens, and no metric reads them yet.
JudgePanel, Disputed, CalibrationNo panel, no disputed outcome, and no calibration gate on CampaignPlan.check. JudgeCalibrationTest measures agreement and reports it, and gates nothing.
AkkaEvaluator, AgentTarget, EvalKitSupportNo such type exists. A campaign against an Akka agent extends TestKitSupport and calls the component client.
Rubrics in a PromptTemplate entityRubric.load reads the classpath. The SDK's own evaluators resolve prompts through a PromptTemplate entity, and adopting that would give a rubric runtime updatability.

Conformance and the SDK contract

PortedMetrics and SdkContract record what this repository claims about code it did not write, and a test fails the build when a record and the code disagree with each other.

PortedMetrics names every metric taken from DeepEval, the upstream class, the file and the commit. An entry is pinned when upstream ships expected values that the fixture reproduces. An entry is unpinned when upstream ships none, and an unpinned entry states why. ToolPermission, TurnRelevancy, TurnFaithfulness, CitationFaithfulness and the decision graph are pinned. The six agentic metrics are unpinned, because the upstream tests for them skip without an API key and assert nothing about the score.

SdkContract names the Akka SDK types this kit is shaped against and the commit they were read at. A reflection pass in evalkit-akka checks every recorded member against the published classes. That pass found one wrong assumption out of seventy, in an entry whose members were inferred from class documentation.

ConformanceCoverageTest scans the metric package and fails when a metric carries no entry, when an entry names a metric that no longer exists, or when an unpinned entry states no reason. The scan covers Metric and AlignmentMetric, because a coverage check that examines the first passes by never looking at the second.

Changes to make before 1.0

Every change below moves a published signature, so each one belongs before a version anybody depends on.

  • Settle the SDK dependency, because the pin on a hand-built SDK decides whether evalkit-akka ships.
  • Decide what a grade from rubric v2 exports. The SDK's Evaluation requires an explanation and makes the score optional, and a v2 grade has no explanation to give.
  • Record an agent's plan and steps. Evidence reads reasoning from the model calls a target reports, and a target that reports none leaves two metrics with nothing to score.
  • Raise Surefire from 2.22.2.
  • Claim a groupId.

The site documentation in docs/site/evalkit/ and docs/design-history.md describe the same code. Where this document and the code disagree, the code is right and this document is a defect.
