Publishing readiness

evalkit builds, runs its tests, and keeps evalkit-core free of dependencies. A Maven Central release additionally requires a licence file, POM metadata and four plugins. The table lists each item and the action it needs.

The aggregator cannot carry the release configuration

evalkit-core has no parent. evalkit-akka inherits akka-javasdk-parent, which supplies the build its TestKit requires. Making the aggregator the parent broke that configuration once already.

Add an evalkit-parent POM holding the release plugins, and have evalkit-core, evalkit-formats and evalkit-junit inherit it. Declare the same plugins a second time inside evalkit-akka.

README contents

The README opens with one sentence naming the behaviour. evalkit runs recorded scenarios against a conversational service and prints a report of the result.

Four behaviours follow, each stated as a mechanism:

  • RunOutcome separates a wrong answer from a run that produced no result, across four variants.
  • CampaignPlan.check refuses an unsatisfiable campaign before the first model call.
  • Scoring.compare throws when two verdict sets carry different rubric versions.
  • CampaignReport exposes counts and no combined pass rate.

Two further statements appear in the README. evalkit-core compiles against the JDK alone, so a service in any language behind a port is evaluated by implementing SystemUnderTest. docs/design-history.md records the incident that produced each design rule, including a campaign that reported 53 outcomes for 80 scenarios and an audit that passed for nine development stages while its regex matched nothing.

The README is the one document in the repository that states rationale. Every page under docs/site/ states behaviour, inputs, outputs and failure modes.

Module design

The library splits into four Maven modules. evalkit-core requires nothing beyond the JDK. evalkit-formats, evalkit-junit and evalkit-akka each add one dependency and the capability that needs it, so a team evaluating a service outside Akka depends on evalkit-core alone.

ModuleContentsDepends on
evalkit-coreScenarios, precursors, the runner, the deterministic, heuristic and agentic scorers, outcomes and reports.The JDK
evalkit-formatsCorpus loaders for JSONL and CSV, the DeepEval golden importer, JSON report output.A JSON library
evalkit-junitThe @Eval annotation and the JUnit 5 extension, for a Java target outside Akka.JUnit 5
evalkit-akkaCampaignWorkflow, agent judges, EvalKitSupport, built-in evaluator adapters, the PromptTemplate rubric source.Akka SDK

A type belongs in evalkit-core when it decides which numbers the report prints. Scoring, outcome classification, the plan check and reporting each decide that, so evalkit-core holds them. Reading a file, driving a test lifecycle and hosting an agent decide nothing about the report, so those types live in the module that supplies the dependency they need.

evalkit-formats holds the corpus readers, which keeps a JSON library off the classpath of a team that builds its scenarios in code. evalkit-formats also holds a reader for DeepEval goldens, so a team already running DeepEval can point a campaign at its existing corpus without rewriting the file.

Package design

evalkit-core replaces its domain and application packages with dataset, runner, scorer and reports. The domain and application names describe the layers of a service, and this library has no service layers.

io.akka.evalkit ├── dataset Scenario, Precursor, ScenarioSource, Corpus ├── runner SystemUnderTest, ScenarioRunner, Recording, CampaignPlan, CampaignRunner, Lanes ├── scorer Scorer, ScorerRouter, RunOutcome, Verdict, Band, Scoring │ ├── deterministic NodeMatch, ExactMatch, ContainsAll, JsonSchemaMatch, ToolCallMatch │ ├── heuristic Metric, MetricRef, LatencyBudget, TokenBudget, JsonValidity, Similarity │ └── agentic Judge, Rubric, RubricSource, Panel, Quorum, Calibration └── reports CampaignReport, RunSummary, Tokens

The consuming project's src/eval/java tree repeats these package names for its own scorers, target adapters and corpus loaders.

API surface: dataset

A Scenario holds its setup as a Precursor value. Parsing the setup out of a scenario title with a regular expression instead produced scores of 23, 17 and 19 out of 40 across three versions of that expression, on a service that never changed.

package io.akka.evalkit.dataset;

/** Reaches a state, says the graded turn, and expects a stated outcome. */
public record Scenario(String id,
                       Optional<String> specNode,
                       Optional<MetricRef> metric,
                       Precursor precursor,
                       String gradedTurn,
                       String expectedOutcome) {

    public static Builder named(String id);
    public boolean needsJudge();          // no node and no metric
    public Scenario via(Precursor other);

    public static final class Builder {
        public Builder  from(Precursor precursor);
        public Builder  say(String gradedTurn);
        public Scenario expect(String expectedOutcome);   // judged
        public Scenario reaches(String specNode);         // deterministic
        public Scenario within(MetricRef metric);         // heuristic
    }
}

/** How the service is put into the state a scenario assumes. */
public sealed interface Precursor {
    record None() implements Precursor {}
    record Replay(List<String> userTurns) implements Precursor {}
    record Fixture(String name, Map<String, String> parameters) implements Precursor {
        public static Fixture named(String name);
    }
    static Precursor replay(String... userTurns);
    default boolean provesReachability();   // true only for Replay
    default String  describe();
}

/** Where a campaign's scenarios come from. Paged, so a restart reads a cursor. */
public interface ScenarioSource {
    int size(String campaignId);
    List<Scenario> page(String campaignId, int offset, int limit);
}

/** An in-memory source, for a campaign small enough to hold. */
public final class Corpus implements ScenarioSource {
    public static Corpus of(Scenario... scenarios);
    public static Corpus of(List<Scenario> scenarios);
}

Usage

// A corpus written in code. Each scenario declares the state it assumes.
var corpus = Corpus.of(

    // Judged: the expected outcome is prose, so a rubric settles it.
    Scenario.named("refund-30d")
        .from(Precursor.Fixture.named("authenticated-claim-open"))
        .say("What if these shoes don't fit?")
        .expect("a 30-day full refund at no extra cost"),

    // Deterministic: the expectation names a node, so comparison settles it.
    Scenario.named("GenUC-16a.3")
        .from(Precursor.replay("I lost my bag", "it arrived yesterday"))
        .say("so what happens now?")
        .reaches("GenUC-16a.3"),

    // Heuristic: the expectation names a metric and its version.
    Scenario.named("faq-latency")
        .from(new Precursor.None())
        .say("how long do refunds take?")
        .within(new MetricRef("latency-budget", 1)));

// A fixture with parameters. The target reads them when it builds the state.
var inFrance = new Precursor.Fixture("authenticated-claim-open",
    Map.of("country", "FR", "wallet", "none"));

// The same scenario reached a different way. Walking proves the path exists.
Scenario walked = corpus.page("refund-policy", 0, 1).get(0)
    .via(Precursor.replay("hello", "I bought shoes last week"));

A source must be stable across pages

page returns the same scenarios for the same offset on every call. A source that reorders between waves causes a restart to skip some scenarios and repeat others. The skipped and repeated scenarios cancel out in the totals, so the campaign reports a count that matches the corpus size while covering less of it.

API surface: runner

ScenarioRunner produces a Recording and assigns no score. Scoring reads the Recording afterwards. A rubric applies to stored recordings without running the conversations again, and one rubric version can score a recording this library produced alongside a recording made elsewhere.

Usage: a target outside Akka

// A chat service behind HTTP. java.net.http ships with the JDK, so this
// adapter adds no dependency to evalkit-core.
public final class HttpChatTarget implements SystemUnderTest {

    private final HttpClient http = HttpClient.newHttpClient();
    private final URI base;
    private final Function<String, String> readReply;   // caller supplies JSON parsing

    @Override
    public Prepared prepare(Precursor precursor) {
        return switch (precursor) {
            case Precursor.None ignored -> new Prepared.Ready(newSession(), "");

            case Precursor.Fixture fixture -> {
                var response = post("/test/fixtures/" + fixture.name(), fixture.parameters());
                yield response.statusCode() == 200
                    ? new Prepared.Ready(readReply.apply(response.body()), "")
                    // Never throw for an expected failure. A precursor that cannot
                    // land becomes NotReached, which is a fact about the campaign.
                    : new Prepared.Failed("fixture returned " + response.statusCode());
            }

            case Precursor.Replay replay -> {
                String session = newSession();
                StringBuilder history = new StringBuilder();
                for (String turn : replay.userTurns()) {
                    var reply = submit(session, turn);
                    history.append("User: ").append(turn)
                           .append("\nAgent: ").append(reply.text()).append("\n\n");
                }
                yield new Prepared.Ready(session, history.toString());
            }
        };
    }

    @Override
    public Reply submit(String sessionId, String userText) {
        var started = Instant.now();
        var body = post("/chat/" + sessionId, Map.of("message", userText)).body();
        return new Reply(readReply.apply(body), Optional.empty(),
                         Optional.of(Duration.between(started, Instant.now())), List.of());
    }

    @Override
    public Map<String, String> fixtures() {
        // The target declares the states it can build. A campaign naming a fixture
        // missing from this map is refused before the first call.
        return Map.of("authenticated-claim-open",
                      "a signed-in customer with one claim open and no wallet");
    }

    @Override
    public Accounting spend() {
        // This service reports no usage. Returning the default makes the
        // report print the total as a floor and name the unaccounted calls.
        return new Accounting(Tokens.NONE, 1);
    }
}

Usage: planning and running a campaign

var target = new HttpChatTarget(URI.create("http://localhost:8080"), Json::readReply);
var judge  = new AnthropicJudge(Rubric.load("scenario-judge", 2));
var router = ScorerRouter.byExpectation(judge,
    Map.of(new MetricRef("latency-budget", 1), LatencyBudget.under(Duration.ofSeconds(4))));

var plan = new CampaignPlan("refund-policy",
    corpus.page("refund-policy", 0, 500), Lanes.of(8), router);

// The plan check runs first and refuses before any spend.
switch (plan.check(target)) {
    case CampaignPlan.Check.Refused refused -> {
        refused.reasons().forEach(System.err::println);
        return;
    }
    case CampaignPlan.Check.Ready ready -> System.out.println(RunSummary.scope(ready.plan()));
}

CampaignRunner.Result result = CampaignRunner.run(plan, target, router);

// Every outcome travels with the scenario that produced it.
for (CampaignRunner.Completed completed : result.completed()) {
    System.out.printf("%-24s %s%n",
        completed.scenario().id(), completed.outcome().describe());
}

System.out.println(result.utilisation().summary());
// 7.4 of 8 lanes (92%), 1.9/s over 271s — lane-bound; more lanes would help

Completed carries the scenario that produced the outcome

Outcomes and scenarios were once returned as parallel lists appended by concurrent workers. Under six lanes, submission order and completion order differ, and a per-scenario report attributed results to the wrong requirement. A bare List<RunOutcome> return type puts the same pairing problem in the caller, so Completed is public and holds both values.

API surface: scorer

Scorer.score returns RunOutcome. A double return type has no value meaning "not scored", so a scorer that failed would have to return a number, and the report would count that number as a score.

package io.akka.evalkit.scorer;

    RunOutcome score(Recording recording);

}

    Scorer scorerFor(Scenario scenario);

public sealed interface RunOutcome {

    record Scored(Verdict verdict) implements RunOutcome {}

    record Unscoreable(String reason) implements RunOutcome {}

    default boolean isEvidence();    // Scored, Asserted, Measured
    default boolean passed();
    default boolean needsReview();   // middle band, or Disputed
    default String  describe();
}

Usage: reading an outcome

// The switch is exhaustive and carries no default, so a sixth variant fails to compile.
String row = switch (outcome) {
    case RunOutcome.Scored s ->
        "%s %d/10 under %s".formatted(s.verdict().band(), s.verdict().score(),
                                    s.verdict().rubricId());
    case RunOutcome.Asserted a -> a.passed()
        ? "reached " + a.expected()
        : "expected %s, reached %s".formatted(a.expected(), a.actual());
    case RunOutcome.Measured m ->
        "%s %.2f against %.2f".formatted(m.metricId(), m.value(), m.threshold());
    case RunOutcome.Disputed d ->
        "%d judges disagreed".formatted(d.verdicts().size());
    case RunOutcome.NotReached n -> switch (n.cause()) {
        case SETUP_FAILED -> "never reached the question — " + n.reason();
        case NO_REPLY     -> "no reply — " + n.reason();
    };
    case RunOutcome.Unscoreable u -> "unscoreable — " + u.reason();
};

// Scored, Asserted and Measured return true. NotReached, Unscoreable and
// Disputed return false and stay out of the pass-rate denominator.
long evidence = outcomes.stream().filter(RunOutcome::isEvidence).count();

Usage: a custom scorer

Inside an Akka service a judge is an Agent, covered in the Akka SDK components section. The scorer below calls a provider directly, which is the shape for a campaign running against a service outside Akka with no runtime present.

// A judge that calls a provider directly. No Akka runtime is involved.
public final class AnthropicJudge implements Judge {

    private final Rubric rubric;
    private final AnthropicClient client;

    @Override public Rubric rubric() { return rubric; }
    @Override public String id()      { return rubric.label(); }

    @Override
    public RunOutcome score(Recording recording) {
        Transcript transcript = recording.transcript();
        String reply;
        try {
            reply = client.complete(rubric.instructions(), rubric.data(transcript));
        } catch (RuntimeException e) {
            // A refusal, a filter or a timeout tells us nothing about the service.
            return new RunOutcome.Unscoreable(e.getMessage());
        }

        return Verdict.parseScore(reply)
            .<RunOutcome>map(score -> new RunOutcome.Scored(
                Verdict.of(transcript.scenarioName(), rubric, score, "")))
            // An unreadable reply is never defaulted. A fabricated score moves
            // the band distribution and nothing in the report would show it.
            .orElseGet(() -> new RunOutcome.Unscoreable("no score in: " + reply));
    }
}

Heuristic scorers

package io.akka.evalkit.scorer.heuristic;

public record MetricRef(String metricId, int version) {}

public interface Metric extends Scorer {
    MetricRef ref();
    double measure(Recording recording);
    double threshold();
}

public final class LatencyBudget implements Metric { public static LatencyBudget under(Duration limit); }
public final class TokenBudget   implements Metric { public static TokenBudget under(long tokens); }
public final class JsonValidity  implements Metric { public static JsonValidity required(); }
public final class Similarity    implements Metric {
    public static Similarity cosine(Embedder embedder, double threshold);
}

/** Supplied by the caller, so core carries no model client. */
public interface Embedder { float[] embed(String text); }
// Two metrics that read a property of the service and carry no interpretation.
Metric latency = LatencyBudget.under(Duration.ofSeconds(4));
Metric tokens  = TokenBudget.under(2_000);

// A metric of your own. The version changes whenever the threshold or the
// formula changes, and Scoring.compare throws across versions.
public final class AnswerLength implements Metric {

    @Override public MetricRef ref()      { return new MetricRef("answer-length", 2); }
    @Override public String    id()       { return "answer-length v2"; }
    @Override public double    threshold() { return 400; }

    @Override
    public double measure(Recording recording) {
        return recording.transcript().systemOutput().length();
    }

    @Override
    public RunOutcome score(Recording recording) {
        double value = measure(recording);
        return new RunOutcome.Measured(ref().metricId(), ref().version(),
                                       value, threshold(), value <= threshold());
    }
}

A threshold change alters every result recorded under the old threshold

Raising a similarity threshold from 0.75 to 0.80 turns some passing runs into failing ones with no change to the service. MetricRef stamps each Measured outcome with the metric id and version, and Scoring.compare throws when the two sides carry different metric versions. Bump the version whenever a threshold or a formula changes.

Usage: panels and calibration

// Three judges score the same transcript under different rubrics.
Panel panel = Panel.of(
        new AnthropicJudge(Rubric.load("scenario-judge", 2)),
        new GeminiJudge(Rubric.load("scenario-judge", 2)),
        new AnthropicJudge(Rubric.load("scenario-judge-strict", 1)))

API surface: reports

CampaignReport exposes counts per outcome and per precursor, and no combined percentage. A campaign produces asserted runs alongside judged runs, measured runs, and runs that returned no evidence. A single percentage over that mixture would count a judged borderline verdict and a deterministic comparison as results of the same kind.

public record CampaignReport(/* counts by outcome and by precursor */) {

    public static CampaignReport of(List<RunOutcome> outcomes, List<Precursor> precursors);
    public static CampaignReport empty();
    public CampaignReport plus(CampaignReport other);       // wave accumulation

    public int total();
    public int judged();        public int asserted();
    public int measured();      public int disputed();
    public int review();        public int passed();
    public int notReached();    public int unscoreable();

Every judge is an Agent. A panel measuring agreement is an Autonomous Agent declaring Delegation, whose workers run with partitioned context. A panel where one judge answers another is an Autonomous Agent declaring Moderation, whose participants share a conversation.

Moderation shares the conversation, so it cannot measure agreement

Inter-rater agreement requires each judge to score without seeing another judge's verdict. Under Moderation a participant receives the conversation entries added since its last turn, so the second judge answers the first. The resulting figure measures the conversation.

Delegation isolates workers from each other, which is the property a measured agreement figure needs. Use Moderation for a refutation pass, where the second judge reads the first judge's verdict and argues against it.

Judges

// Scores a single transcript in one model round-trip, with memory off.
// A judge holding session memory drifts toward its own recent scores, and
// two campaigns run in a different order then disagree on the same reply.
@Component(id = "scenario-judge", name = "Scenario Judge",
    description = "Scores a recorded conversation against its expected outcome.")
@AgentRole("evaluator")
public class ScenarioJudge extends Agent {

    public record Result(String explanation, boolean passed, int score, Band band)
        implements EvaluationResult {}

    public Effect<Result> judge(JudgeRequest request) {
        return effects()
            // The rubric arrives from PromptTemplate, so the wording carries a
            // revision and changes without a redeploy.
            .systemMessageFromTemplate(request.rubric().templateKey())
            .memory(MemoryProvider.none())
            .userMessage(request.rubric().data(request.transcript()))
            .map(reply -> toResult(reply, request))
            .thenReply();
    }
}

The return type implements EvaluationResult, so the runtime records every verdict in metrics and traces without further instrumentation.

Autonomous Agents are not replicated across regions

The SDK documentation states that Autonomous Agent instances stay in the region where they were created and that tasks replicate like any other entity. A campaign that has to survive the loss of a region runs its judges as request-based Agents under CampaignWorkflow, whose state replicates.

The seven files that assert a value all separate the model's verdicts from the arithmetic applied to them. ScriptedJudge in test_turn_relevancy_aggregation.py extends DeepEvalBaseLLM, returns a list of prepared verdicts in order, and the test asserts the exact score.

The model half of a metric samples and cannot be pinned. The arithmetic half is a pure function of the verdicts, and a port gets that half wrong silently. Splitting the interface makes the testable half testable.

package io.akka.evalkit.scorer.heuristic;

/** A model verdict about a single claim, exchange or tool call. */
public record Judgement(String subject, boolean affirmed, String reason) {}

/** A metric whose score is computed from model verdicts. */
public interface JudgedMetric extends Scorer {

    MetricRef ref();

    /** Asks the model. Samples, needs a provider, cannot be pinned. */
    List<Judgement> collect(Recording recording);

    /** A pure function of the verdicts. Runs with no model and no key. */
    RunOutcome aggregate(List<Judgement> judgements);

    @Override default RunOutcome score(Recording recording) {
        return aggregate(collect(recording));
    }
}

# evalkit

**The evaluation harness for conversational services.**

[![Build](https://github.com/tylerjewell/evalkit/actions/workflows/build.yml/badge.svg)](https://github.com/tylerjewell/evalkit/actions/workflows/build.yml)
[![License](https://img.shields.io/badge/license-Apache%202.0-blue.svg)](LICENSE)
[![Java](https://img.shields.io/badge/java-21%2B-orange.svg)](https://openjdk.org/projects/jdk/21/)

[Quickstart](#quickstart) · [Metrics and features](#metrics-and-features) ·
[Integrations](#integrations) · [Reports](#a-report) ·
[Contributing](CONTRIBUTING.md) · [Documentation](docs/site/evalkit/)

evalkit is an open-source evaluation harness for conversational services, written
in Java. The harness is similar to JUnit and specialized for services that hold a
conversation: it puts the service into a known state, sends one message, scores
the reply against a stated expectation, and prints a report a compliance reader
can act on. A reply is scored by comparison against a named requirement, by a
metric that computes a number, or by a model reading the transcript against a
versioned rubric, and the harness records which of the three settled each run.

The words below are used throughout. A **scenario** describes one test: an id, the
state the service has to be in before the test starts, the message to send, and
the answer expected back. A **corpus** is a list of scenarios. A
**campaign** is one run of a corpus against one service, and it produces one
report. A **judge** is a model that reads a transcript against a rubric and
returns a score from 1 to 10.

## Metrics and features

**Metrics ported from DeepEval**, each pinned to the expected values in DeepEval's
own tests at a recorded commit:

| Metric | Scores | Model calls |
|---|---|---|
| `ToolPermission` | Whether an agent called only the tools it was allowed to call | 0 |
| `TurnRelevancy` | The share of exchanges whose reply answered what was asked | 1 per exchange |
| `TurnFaithfulness` | The share of claims in a reply that the retrieved passages support | 1 per claim |
| `CitationFaithfulness` | Whether each citation points at a passage supporting the claim beside it | 1 per citation |
| `Dag` | The branch a judge chose through a decision graph | 1 per judgement node |

**A scenario naming a specification node costs no model call.** The scorer
checks which node the reply reached. A scenario naming a metric with
deterministic judgements is settled by arithmetic. On one recorded corpus, 510 of
514 scenarios were settled this way, which is what makes a large corpus
affordable.

**A judge reads the transcript against a versioned rubric.** A rubric is a
judge's prompt, held as data under `resources/rubrics/` and loaded by id and
version. Every `Verdict` carries the id and version that produced it, and
`Scoring.compare` refuses to compare scores across versions.

**`RunOutcome` separates a failure from an absence.** The sealed interface has
five variants. `Scored`, `Asserted` and `Measured` mean the service answered and
the answer was assessed. `NotReached` means the setup never completed, and
`Unscoreable` means the judge produced nothing readable. The last pair stays out
of the pass total.

**A campaign is refused before it runs.** `CampaignPlan.check` asks the service
which states it can build and which answers it can produce, compares those
against what the corpus needs, and refuses a campaign that cannot succeed.

**A scenario reaches its starting state by replay or by seeding.**
`Precursor.replay` walks the recorded turns through the same interface a user
would use, which is slow and proves the state is reachable. `Precursor.fixture`
asks the service to write the state directly, which costs no model calls.

**`RunSummary` writes for a reader who cannot check the work.** The report is
terminal-width plain text, and it states what will be tested before the run, what
was found after, the judge's bands and its measured agreement with a human
reviewer, and what the run cannot show. `Accounting` counts the model calls whose
token usage the service could not report, and labels the total a floor.

**A campaign bounds its concurrency and survives a restart.** `Lanes` sets how
many scenarios run at once. In an Akka project a campaign is a workflow that
writes a cursor after each wave, so a restart repeats one wave instead of the
whole campaign.

**A conformance suite pins each ported metric to its upstream values.**
`io.akka.evalkit.conformance` holds those fixtures, and
`ConformanceCoverageTest` fails the build when a ported metric has no fixture,
when a fixture names a metric that no longer exists, or when an entry records no
upstream commit.

## What evalkit adds

DeepEval established the metric shapes this project ports. The behaviour below
has no counterpart there.

**A run that produced no result is never a failure.** A judge that times out or
refuses gives `Unscoreable`, and a setup that does not complete gives
`NotReached`. The report keeps both out of the pass rate, because neither result
says anything about the service.

**A report prints no single pass-rate number.** A campaign mixes exact
comparisons, threshold computations and model verdicts. Averaging them gives a
borderline model verdict the same weight as an exact match, so `CampaignReport`
keeps the three in separate columns and prints no combined figure.

**A deterministic result is a pass or a fail, never undecided.** A comparison
either matched or missed, and a number is either inside its threshold or outside
it. The undecided column shows a dash for both, and a figure in either cell means
this kit has a bug.

**Campaigns survive a restart.** In the Akka module a campaign is a durable
workflow, so an hours-long run resumes after a deploy.

## Integrations

**`evalkit-core` evaluates any service reachable over a port.** The module
requires Java 21, declares no compile dependencies, and uses JUnit 5 and AssertJ
for its own tests. A service written in any language is evaluated by implementing
one interface.

```java
public interface SystemUnderTest {
    Prepared prepare(Precursor precursor);       // get into position
    Reply submit(String sessionId, String userText);
    Map<String, String> fixtures();              // states this service can build
}
```

**`evalkit-akka` runs a campaign inside an Akka project.** The campaign becomes
a durable workflow, judges become Akka agents, and the whole service starts under
the Akka TestKit, so the campaign calls the real agents.

**A campaign runs as an ordinary JUnit 5 test.** The result reports through the
same build and the same CI job as the rest of the suite.

## Quickstart

### Installation

```xml
<dependency>
  <groupId>io.akka.evalkit</groupId>
  <artifactId>evalkit-core</artifactId>
  <version>0.1.0-SNAPSHOT</version>
</dependency>
```

### Write your first scenario

A **specification node** is the identifier of the requirement a scenario
exercises, and `REFUND-004` below is one.

```java
var corpus = List.of(
    new Scenario("refund-outside-window",
        Optional.of("REFUND-004"),                       // the requirement it exercises
        Precursor.replay("I want a refund", "order 4417"),
        "It has been 45 days. Can I still return it?",
        "Refuses, and states the 30-day window"));
```

### Run the campaign

`Lanes.of(8)` runs eight scenarios at a time. `target` is the `SystemUnderTest`.
The router is a `ScorerRouter`, which decides for each scenario whether the result
is settled by comparison, by a metric or by a model.

```java
var plan = new CampaignPlan("refund-policy", corpus, Lanes.of(8), router);

switch (plan.check(target)) {
    case CampaignPlan.Check.Refused r -> { r.reasons().forEach(System.err::println); return; }
    case CampaignPlan.Check.Ready ready -> System.out.println(RunSummary.scope(ready.plan()));
}

var result = CampaignRunner.run(plan, target, router);
System.out.println(RunSummary.of(result).render());
```

`plan.check(target)` runs before any call goes out, so a campaign that would fail
at minute forty for a reason knowable at minute zero stops in the first second.

### Use a metric on its own

A **judgement** is one yes-or-no observation about a reply, such as whether a
single tool call was authorised. A **metric** turns a list of judgements into a
number and compares that number against a threshold. Collecting the judgements
may call a model. Turning them into a number is a pure function, so `aggregate`
runs in a unit test with no provider and no key.

```java
var metric = ToolPermission.allowing("search_kb", "reply");
var judgements = metric.judge(List.of("search_kb", "delete_account"));

metric.aggregate(judgements);                 // 0.5
metric.withinThreshold(0.5);                  // false
ToolPermission.unauthorised(judgements);      // ["delete_account"]
```

### Run inside an Akka project

Add `evalkit-akka`, extend `EvalKitSupport`, and the campaign starts the service
under the Akka TestKit and calls the deployed agents through the component client.
Building this module needs the Akka SDK, which the [Build](#build) section covers.

## How a scenario is settled

Every scenario is routed to one of the three families below before any call goes
out.

| Family | Settles the result by | Model calls |
|---|---|---|
| Comparison | The reply reached the node the scenario named. | 0 |
| Computation | A metric scored the reply against a threshold. | 0 |
| Judgement | A model read the transcript against a versioned rubric. | 1 or more |

## What a run produces

Every scenario a campaign ran produces a row, and the row carries one of these.

| Outcome | What happened | Counted |
|---|---|---|
| `Scored` | A judge read the reply and gave it a score. | Yes |
| `Asserted` | The reply was compared against a stated answer. No model was involved. | Yes |
| `Measured` | A metric computed a number and compared it to a threshold. | Yes |
| `NotReached` | The setup failed, or the service sent nothing back. | No |
| `Unscoreable` | The judge timed out, refused, or returned something unreadable. | No |

Counted means the run is included when the report works out how many scenarios
passed. A run that is not counted gets its own line with its own reason.

`RunOutcome` is a sealed interface. Switches over it are exhaustive and carry no
`default`, so a new outcome is a compile error at every site handling one.

## What a report will not show

A report never prints:

- one pass-rate percentage for the whole campaign
- an undecided result for a check settled by comparison or by a threshold
- a zero for a run the judge would not score
- a token total the service could not measure, printed as a measurement
- any result at all when the service cannot satisfy the scenarios

A reader would quote any of those figures. The report prints counts by category
instead, and the categories that belong together add up.

## Why the outcomes are split this way

A low score by itself does not distinguish a wrong answer from a run that never
asked the question.

**The service answered and the answer was wrong.** `Scored`, `Asserted` and
`Measured` record a service that answered, whichever way the answer came out.

**The setup never completed.** A scenario needing a signed-in customer with an
open claim replays earlier turns or seeds the state directly, and a failure in
that step means the graded question was never asked. `NotReached` records it.

**The judge produced nothing to read.** During calibration a content filter
refused to score a transcript about a failed identity check. `Unscoreable`
records it.

Scoring a `NotReached` or an `Unscoreable` run as zero reports a working service
as a broken one, so the report counts both on their own lines.

A **band** is one of the three ranges a judge's score falls into: 8 to 10 matched,
4 to 7 matched in part, 1 to 3 did not match. A judge and an independent reviewer
agreed on 89 to 91 percent of clear replies and on 53 percent of the replies
scoring in the middle band, which is close enough to chance that the middle band
counts as undecided and never as a pass.

One corpus stated its expected answers without stating the inputs those answers
depend on, so an early version parsed the inputs from the scenario titles with a
regular expression. The same unchanged service scored 23, 17 and 19 out of 40
under three versions of that expression, and a scenario now states its own setup
as data.

## Build

evalkit builds with Java 21 and Maven.

```shell
mvn -pl evalkit-core test    # the whole of evalkit-core, no setup needed
mvn install                  # adds evalkit-akka
```

`evalkit-akka` depends on the Akka SDK, which is not published to Maven Central.
The Akka Specify plugin puts it on your machine:

1. Install the Akka Specify plugin in your AI coding assistant, following
   [the setup guide](https://doc.akka.io/getting-started/set-up-dev-env.html).
2. Run `/akka:setup`, which configures the CLI, Java, Maven and your Akka
   download token, and writes the repository into `~/.m2/settings.xml`.
3. Run `mvn install`.

Continuous integration builds `evalkit-akka` where that repository URL is
configured as the `AKKA_MAVEN_REPO_URL` secret, and covers `evalkit-core`
everywhere.
